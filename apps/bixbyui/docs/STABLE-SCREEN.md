# 画面稳定后再读 + 编号核对（stable-screen）

手机执行层（`PhoneAgent` + 读屏助手 / 无障碍后端）每做一个动作，都要读一次界面树交给模型。
动作刚做完时界面常在转场、加载、弹出动画里，只读一次可能拿到半截画面；模型思考的几秒里界面也可能自己变了（加载完、弹窗、列表刷新），
这时按旧编号、旧坐标去点就会点错。本改动补上这两处。

思路参考开源项目 agent-phone（<https://github.com/lurenss/agent-phone>，Apache-2.0）：
`snapshot --settle`（读到几次一致才算画面停了）和「ref 必须来自最后一次输入之后的快照，执行时在新读到的树上重新找到元素，找不到就明确拒绝」。
代码按思路自己写，**没有复制其源码**，因此不需要在 NOTICE / THIRD_PARTY_NOTICES 里加条目。

## 1. 画面稳定再读（`StableRead`）

- 动作（点击 / 长按 / 输入 / 滑动 / 按键 / 打开 App / 收集列表时的翻页）之后，原来是「等事件安静 → 读一次」；
  现在是「等事件安静 → 读 → 隔 150 ms 再读 → 指纹一致就用这一屏，不一致继续，最长 1.5 s」。
- 指纹：`UiTree.settleFingerprint()` = 前台包名 + 页面 + 输入法 + 每个元素的类名 / 资源 id / 文字 / **边界** / 状态的 FNV-64 哈希；
  不含编号（同一画面重读两次一定一致），含边界（滑入动画里元素在动也算没稳定；原来的 `signature()` 不看位置，分不出来）。
- 超时：用最后一次读到的那屏，`Result.trace` 记 `settle unstable …`，Logcat 记 `[PHONE] 读屏 unstable：…`，
  给模型的这一步结果后面加「界面仍在变化（等了 1500ms 没稳定，读的是最后一次）」。
- 带条件的步骤（`expect` / `expect_gone` / `expect_app`）：条件看起来成立时再确认一次稳定，用稳定后的那屏重判；
  稳定不了也按最后一次判（不会因为页面上有倒计时就拖到条件超时）。`wait_stable` 自己就要两次一致、`wait` 步骤之前没有动作，这两种不再额外确认。
- 不等的路径：任务开始的第一次读屏、用户接手 / 确认之后的重读、模型提问之后的重读 —— 这些是查询，仍然只读一次。
- mika 插件 `mika.changewait` 打开时动作后走原来的 `ChangeWait`（事件安静 400 ms 且树变了），不叠加本机制。
- 参数是 `StableRead` 里的常量（`POLL_MS = 150`、`MAX_WAIT_MS = 1500`、`MATCHES = 2`、`RECHECK_REFS = true`），
  运行时用 `StableRead.Params`（`PhoneAgent.settle`）可调；`settle = null` 即完全是改前行为（JVM 旧用例都在这个口径下跑）。
- 真机入口 `PhoneHooks.runBlocking` 默认打开；偏好（`PhoneHooks.PREF` 里的 `settle_after_action`）设为 false 可关（排查用）。
  `files/phone_last.txt` 多一行 `settle=… settleReads=… unstable=… refStale=… refMoved=…`。

代价：已经稳定的画面每个动作多 1 次读屏 + 150 ms；一直在变的画面最多多约 1.5 s。

## 2. 编号（ref）核对

**现有机制**：给模型的控件表本来就是每行一个短编号 `[12]`，同一任务里同一元素（资源 id + 名字 + 类名 + 同键序号）换屏后编号不变（`UiTree.Ids`；
mika.refs 打开时是 `RefStabilizer` 的 `@eN`），模型按编号下指令，执行时 `UiTree.find(id)` 映射回元素（边界 / 助手节点下标），
`PhonePlan.validate` 在编号不在当前界面时拒绝执行并把控制交回模型。所以只补缺口：

- **缺口 1：模型思考期间界面变了。** 一批里第一步用的是问模型之前读的那屏。现在执行一批里第一个指名元素的步骤（tap / long / type / scroll 带 id）前，
  先重读一次（单次读，不等稳定），用 `StableRead.checkRef` 核对：
  - 编号还在：按**新读到的位置**执行（记 `ref moved`）；
  - 编号不在了：不执行，报 `REF_STALE：编号 [N]「…」已失效（你看过之后界面变了，它已不在屏上）；已重新读屏，请用新界面里的编号`，新界面交回模型；
  - 位置挪了超过短边 5% 且屏上有同名元素（同键序号可能已经串位）：同样 `REF_STALE`，不猜。
  一批后面的步骤用的是上一步之后（稳定）读到的屏，不再重读。
- **缺口 2：用户确认敏感步骤期间界面变了。** 原来确认后重读只检查编号还在不在；现在也用 `checkRef` 核对（不多读屏）。

改动面约 0.5 天，没有超过 2 天的门槛，所以第 2 点直接做了。

## 需要真机验证

1. 典型转场（设置 → 子页面、App 冷启动、弹窗出现）后模型拿到的是不是终态；`phone_last.txt` 的 `unstable` 次数。
2. 有轮播 / 倒计时 / 跑马灯 / 视频的页面每步是不是都要等满 1.5 s（如果常见，考虑把指纹里的边界放宽或忽略某些区域）。
3. 一次读屏的实际耗时（助手 / B2 后端），稳定判定多出的那次读屏 + 150 ms 对整体任务时长的影响。
4. 动作刚做完、App 还没开始响应时两次读到同一旧画面就判稳定的情况（前面有事件安静等待挡着，需要确认够不够）。
5. mika.refs 打开时，多出来的读屏让 `RefStabilizer` 多走几轮，编号沿用率、结构化差异是否正常。
6. 模型思考期间界面变化的真实场景（加载完成把按钮挤下去、弹出广告）下 `REF_STALE` / `ref moved` 是否按预期。
